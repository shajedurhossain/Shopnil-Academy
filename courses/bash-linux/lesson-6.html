Conditionals & Functions

A script that always does the same thing regardless of input is only half a script. Real pipelines make decisions — skip a sample if its FASTQ is empty, choose a different aligner for paired-end vs single-end reads, retry a failed download. Conditionals give your scripts judgment. Functions let you package that judgment once and reuse it everywhere.

01 if, elif, else — making decisions

🔀 Why conditionals exist

An if statement runs a block of commands only when a condition is true, and skips it otherwise. This is how a script adapts to different situations instead of blindly running the same steps regardless of what it finds.

In bioinformatics this is everywhere: skip a sample if its FASTQ file is empty, choose paired-end alignment settings if a second read file exists, warn the researcher if disk space is low before starting a job that needs 200GB. Without conditionals, a script cannot respond to reality — it can only repeat the same sequence blindly.

The structure is if CONDITION; then COMMANDS; fi. Note that Bash spells "end if" backwards as fi — the same pattern as done closing a loop. elif (short for "else if") checks another condition if the first was false. else catches everything that didn't match any condition above it.

Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash
if [ 5 -gt 3 ]; then
    echo "5 is greater than 3"
fi
5 is greater than 3

# if / else
READS=150
if [ $READS -ge 100 ]; then
    echo "Sufficient read depth"
else
    echo "Warning: low read depth"
fi
Sufficient read depth

# if / elif / else — three-way decision
QUALITY=28
if [ $QUALITY -ge 30 ]; then
    echo "High quality"
elif [ $QUALITY -ge 20 ]; then
    echo "Acceptable quality"
else
    echo "Low quality — consider re-trimming"
fi
Acceptable quality
⚠

The spaces inside [ ] are mandatory. [$READS -ge 100] without spaces around the brackets fails with a confusing error. Always write it as [ condition ] with a space right after [ and right before ].

02 Test operators — numbers and files

🧮 Why -eq instead of ==

Inside [ ], Bash uses word-based comparison operators for numbers rather than symbols like > or == — because > already means output redirection inside [ ] and would silently create a file instead of comparing anything. -eq, -gt, and friends avoid that collision entirely.

File test operators are just as important in bioinformatics as number comparisons. Before you run an aligner, you check the input actually exists with -f. Before you write output, you check the destination folder exists with -d. Before you trust a download finished, you check the file isn't empty with -s.

OperatorTrue when
-eqNumbers are equal
-neNumbers are not equal
-gtLeft number is greater than right
-geGreater than or equal to
-ltLess than
-leLess than or equal to
-f FILEFILE exists and is a regular file
-d DIRDIR exists and is a directory
-s FILEFILE exists and is NOT empty (size > 0)
-r / -w / -x FILEFILE is readable / writable / executable
! CONDITIONNegates any condition — true becomes false
Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash
# File existence check
if [ -f species.txt ]; then
    echo "species.txt exists"
fi
species.txt exists

# Directory existence check
if [ -d ../results ]; then
    echo "results folder exists"
fi
results folder exists

# Empty-file check — catches failed downloads that create a 0-byte file
if [ -s sample.fastq ]; then
    echo "sample.fastq has content"
else
    echo "sample.fastq is missing or empty — do not proceed"
fi
sample.fastq has content

# Negation with !
if [ ! -f missing_reference.fa ]; then
    echo "Reference genome not found — cannot align"
fi
Reference genome not found — cannot align

03 String comparisons

🔤 Comparing text, not just numbers

String comparisons use = and != — the ones that would collide with arithmetic if used inside [ ] for numbers, which is exactly why numbers use -eq instead. For strings there is no such collision, so the ordinary symbols work.

-z tests whether a string is empty (zero length) — extremely useful for checking whether an argument was actually supplied and isn't just an empty string. -n is the opposite: true when the string has content.

In bioinformatics, string comparisons decide which branch of a pipeline to run — is this sample "control" or "treated"? Is the file format "fastq" or "fasta"? Is the organism "human" or "sorghum"?

Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash
CONDITION="treated"

if [ "$CONDITION" = "treated" ]; then
    echo "This sample received treatment"
else
    echo "This is a control sample"
fi
This sample received treatment

# Not equal
ORGANISM="sorghum"
if [ "$ORGANISM" != "human" ]; then
    echo "Using non-human reference genome"
fi
Using non-human reference genome

# -z: is the string empty?
SAMPLE_NAME=""
if [ -z "$SAMPLE_NAME" ]; then
    echo "Error: sample name is empty"
fi
Error: sample name is empty

# -n: is the string NOT empty?
SAMPLE_NAME="SRR123456"
if [ -n "$SAMPLE_NAME" ]; then
    echo "Sample name is set: $SAMPLE_NAME"
fi
Sample name is set: SRR123456
💡

Always wrap string variables in double quotes inside [ ] — [ "$CONDITION" = "treated" ] not [ $CONDITION = "treated" ]. If the variable is ever empty or unset, the unquoted version breaks with a syntax error. Quoted, it fails safely.

04 Combining conditions — AND, OR, NOT

🧩 Building compound checks

Real pipeline checks are rarely a single condition. You often need "the file exists AND is not empty" or "the format is fastq OR fasta". Bash gives you && (AND) and || (OR) to combine conditions inside a single [ ] test, or as separate bracket groups joined together.

The two styles below are equivalent — combining inside one [ ] with &&, or joining two separate [ ] tests. The separate-brackets style is generally considered clearer and safer, and is what most bioinformatics scripts use.

Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash
# AND — both conditions must be true
if [ -f sample.fastq ] && [ -s sample.fastq ]; then
    echo "File exists AND has content — safe to proceed"
fi
File exists AND has content — safe to proceed

# OR — either condition can be true
FORMAT="fasta"
if [ "$FORMAT" = "fastq" ] || [ "$FORMAT" = "fasta" ]; then
    echo "Recognised sequence format: $FORMAT"
fi
Recognised sequence format: fasta

# Combined AND inside a single test
READS=85
if [ $READS -ge 50 -a $READS -le 100 ]; then
    echo "Reads within expected range"
fi
Reads within expected range

Short-circuit evaluation: with &&, if the first condition is false, Bash never even checks the second — it already knows the answer is false. This means you can safely write [ -f "$FILE" ] && [ -s "$FILE" ] without worrying about the second check running on a file that doesn't exist.

05 case statements — cleaner multi-way branching

🗂 Why case is better than a long elif chain

When you are checking one variable against many possible values, a long chain of elif statements becomes hard to read. case is built exactly for this situation — matching one value against a list of patterns.

Each pattern ends with ) and each branch ends with ;; (double semicolon) — this tells Bash where one branch stops and the next begins. The *) pattern at the end matches anything not caught above, acting as the default/else case. case also supports wildcard patterns like *.fastq), making it useful for branching on file extensions.

Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash
ORGANISM="sorghum"

case "$ORGANISM" in
    human)
        echo "Reference: GRCh38"
        ;;
    mouse)
        echo "Reference: GRCm39"
        ;;
    sorghum)
        echo "Reference: Sbicolor_v3.1"
        ;;
    *)
        echo "Unknown organism — no reference configured"
        ;;
esac
Reference: Sbicolor_v3.1

# case with wildcard patterns on file extensions
FILE="sample.fastq"

case "$FILE" in
    *.fastq)
        echo "FASTQ file — running QC"
        ;;
    *.fasta)
        echo "FASTA file — running BLAST"
        ;;
    *.bam)
        echo "BAM file — running samtools stats"
        ;;
    *)
        echo "Unrecognised file type"
        ;;
esac
FASTQ file — running QC
💡

Notice case is spelled backwards as esac to close it — the same trick as if/fi and do/done. Once you notice the pattern it becomes easy to remember.

06 Functions — package logic once, reuse everywhere

📦 Why functions exist

A function is a named block of code you define once and call as many times as you like. If you find yourself writing the same three lines in five different places in a script, that is a function waiting to happen.

You already used a function without formally learning it — the log() function from Lesson 5. That is exactly what a function is: a reusable piece of logic with a name.

The syntax is function_name() { commands; }. Note there is no function keyword required in this style (though Bash accepts one) — the parentheses () are what mark it as a function definition. The function must be defined before it is called — Bash reads top to bottom, so a call above the definition fails.

Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash
# Define a simple function with no arguments
greet() {
    echo "Starting pipeline run"
}

# Call it — just use its name like any other command
greet
Starting pipeline run

# Call it again — that's the whole point, reuse without retyping
greet
Starting pipeline run

07 Function arguments and return values

🎯 Functions take arguments the same way scripts do

Inside a function, $1, $2, and so on refer to whatever was passed to the function — not the script. This is a common point of confusion: once you are inside a function, $1 means the function's first argument, even if the script itself was also called with arguments.

Bash functions do not "return" values the way functions in Python or R do. A function has an exit status (0–255) accessible via $?, which is meant to signal success or failure, not to carry data. To send data back, the standard approach is to echo the result and capture it with command substitution $( ) from the caller — exactly the same mechanism you learned for capturing command output in Lesson 4.

Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash
# Function that takes an argument
greet_sample() {
    echo "Processing sample: $1"
}

greet_sample "SRR123456"
Processing sample: SRR123456

# Function that "returns" a value via echo + command substitution
count_reads() {
    FILE="$1"
    LINES=$(wc -l < "$FILE")
    echo $(( LINES / 4 ))
}

# Capture the "return value" with $( )
READS=$(count_reads "sample.fastq")
echo "sample.fastq has $READS reads"
sample.fastq has 3 reads

# Function using exit status to signal success/failure
file_is_valid() {
    if [ -s "$1" ]; then
        return 0   # 0 = success
    else
        return 1   # non-zero = failure
    fi
}

if file_is_valid "sample.fastq"; then
    echo "sample.fastq passed validation"
else
    echo "sample.fastq failed validation"
fi
sample.fastq passed validation
⚠

return in a function only sets the exit status (0–255) — it cannot send back a string or a large number. If you echo a value from inside a function, do not also call return with data — they solve different problems. Use echo + $( ) to pass data back; use return to signal success or failure.

08 A complete script — conditionals and functions together

Here is a script combining everything from this lesson: functions for reusable logic, conditionals for decision-making, and a case statement for organism-specific configuration.

save as: sample_check.sh
#!/bin/bash
# ============================================================
# Script:      sample_check.sh
# Description: Validate a FASTQ file and report its reference
#              genome based on organism name.
# Usage:       bash sample_check.sh FASTQ_FILE ORGANISM
# ============================================================
set -e
set -u

# --- Function: validate that a file exists and is not empty ---
file_is_valid() {
    if [ -s "$1" ]; then
        return 0
    else
        return 1
    fi
}

# --- Function: count reads in a FASTQ file ---
count_reads() {
    LINES=$(wc -l < "$1")
    echo $(( LINES / 4 ))
}

# --- Function: look up the reference genome for an organism ---
get_reference() {
    case "$1" in
        human)   echo "GRCh38" ;;
        mouse)   echo "GRCm39" ;;
        sorghum) echo "Sbicolor_v3.1" ;;
        *)       echo "unknown" ;;
    esac
}

# --- Validate arguments ---
if [ "$#" -ne 2 ]; then
    echo "Usage: bash $0 FASTQ_FILE ORGANISM"
    exit 1
fi

FASTQ="$1"
ORGANISM="$2"

# --- Main logic using the functions above ---
if file_is_valid "$FASTQ"; then
    READS=$(count_reads "$FASTQ")
    REF=$(get_reference "$ORGANISM")

    echo "File:      $FASTQ"
    echo "Reads:     $READS"
    echo "Organism:  $ORGANISM"
    echo "Reference: $REF"

    if [ "$REF" = "unknown" ]; then
        echo "Warning: no reference configured for this organism"
    fi
else
    echo "Error: '$FASTQ' is missing or empty"
    exit 1
fi
Run from: ~/bash-linux-bioinformatics/module-2-scripting
bash — save it, then run it
nano sample_check.sh
# type the script, then Ctrl+O, Enter, Ctrl+X

bash sample_check.sh sample.fastq sorghum
File:      sample.fastq
Reads:     3
Organism:  sorghum
Reference: Sbicolor_v3.1

# Try an organism with no configured reference
bash sample_check.sh sample.fastq zebrafish
Reference: unknown
Warning: no reference configured for this organism

Exercise 5 · ChallengeCombine everything into one script

Create save as: qc_gate.sh. It should accept one argument — a FASTQ filename. Define a function read_count() that echoes the read count of a file. In the main script: validate exactly one argument was given, check the file exists and is not empty, then use the function to get the read count and print "PASS" if reads are 1 or more, otherwise "FAIL".

💬 Hint: combine the argument validation pattern from Lesson 5 with the function pattern from this lesson. Test against sample.fastq.

Show answer 
#!/bin/bash
set -e
set -u

read_count() {
    LINES=$(wc -l < "$1")
    echo $(( LINES / 4 ))
}

if [ "$#" -ne 1 ]; then
    echo "Usage: bash $0 FASTQ_FILE"
    exit 1
fi

FASTQ="$1"

if [ -f "$FASTQ" ] && [ -s "$FASTQ" ]; then
    READS=$(read_count "$FASTQ")
    if [ $READS -ge 1 ]; then
        echo "PASS — $READS reads"
    else
        echo "FAIL — 0 reads"
    fi
else
    echo "FAIL — file missing or empty"
fi

# Test: bash qc_gate.sh sample.fastq -> PASS — 3 reads
